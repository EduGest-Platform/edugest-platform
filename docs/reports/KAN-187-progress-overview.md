# KAN-187 — Aggregate progress overview / Resumen agregado de seguimiento

## EN — Canonical

[KAN-187](https://anasfady87-1789923749606.atlassian.net/browse/KAN-187) is assigned to Elizabeth, due **27 November 2026**. Implemented by Yohanna; sole requested reviewer Anasfady. This stack composes existing academic aggregate queries for a dashboard. It does not duplicate their formulas, add individual learner access or complete the risk-model dependency.

Review/merge in order: contracts/policy → attendance/API → submission counts → competency distributions → privacy/scope regressions. The root targets `dev`; each child targets the preceding branch.

### Contract and periods

`GET /api/v1/cohorts/{cohort_id}/progress-overview` requires a session and all three existing academic aggregate permissions on that cohort. Assigned teachers, scoped coordination and administrators can use their existing permissions; applicants, coders and recruiting staff receive no new grants. Every caller receives `aggregate_only=true`, including roles that can read individual rows through other authorized endpoints.

| Section | Scope/time basis | Interpretation |
|---|---|---|
| `attendance` | Inclusive `attendance_from` / `attendance_to`; omitted bounds retain existing attendance semantics | Existing full/half-day rule and recorded-attendance ratio; missing records remain unrecorded, not absences |
| `submissions` | Current published assignments, evaluated at `as_of` | Existing on-time/late/pending/overdue/reviewed counts; preserves first submission time and review behavior |
| `competencies` | Current framework assigned to the cohort | Existing latest assessment distribution for levels 1–3 plus not-assessed; missing framework/version stays null |

Attendance filters do not filter deliveries or reconstruct historical competency progress. `generated_at` is a generation anchor, not a historical cutoff or transaction-wide snapshot. Independent reads may reflect concurrent changes; do not label the result a historical snapshot.

Attendance sums are **learner-days**, not distinct calendar days. `attendance_rate` is a ratio in 0–1, not a percentage in 0–100, and is null without recorded attendance. Delivery state counts are per published assignment; `reviewed` overlaps delivered states and must not be added to the four exclusive delivery-state counts. Competency counts are per competency, not an overall completion percentage. No new KPI threshold or success formula is accepted by this implementation.

### Reuse and privacy

Attendance queries move into `attendance/queries.py`; existing router helper aliases remain for compatibility. Totals still use `summarize`/`cohort_totals`. Deliveries and competencies call existing service functions with `per_person=False`, then project only aggregate fields. The competency rule is shared from schemas rather than copied from a router. No router handler is invoked internally, avoiding intermediate audit commits.

Existing enrollment eligibility excludes voluntary withdrawals and retains completed enrollments. Existing minimum-group suppression applies to every caller. Suppressed counts remain null and `has_data` also becomes null to avoid disclosing record presence. Unsuppressed false has_data means different missingness by section: no recorded attendance, no assignment/enrollment calculation basis, or no current assessments. It never means zero attendance rate or competency level zero.

The overview has no learner IDs/rows, names, emails, portfolio URLs, submitted content, assessment evidence or free-form attendance reasons. It can show cohort/activity/competency identifiers and labels already available in the aggregate tools. One completion audit is recorded after all sections assemble; a failed section does not commit a success event. Reads of operational tables are unchanged; the audit event is the only intended write.

This endpoint is for dashboard integration, not a new assistant allowlist entry. No SQL is generated by an LLM. Risk scores/alerts, the 70% administrative metric, client-approved KPI definitions, UI integration, new roles and historical reporting are outside scope. No operational models or migrations change.

### Validation limits

Offline tests exercise actual HTTP dispatch, authorization, existing attendance calculation, suppression and explicit projection of service responses containing individual canaries. Their database/principal doubles do not validate real authentication, PostgreSQL persistence, transaction isolation or query performance. PostgreSQL cases compare the overview with existing aggregates using explicit synthetic academic seed and cover scope, privacy, suppression and one completion audit. They were collected, not executed locally. No Jira changes, merge or deployment; CI completion is not awaited.

Evidence on 25 November: 44 offline API/contract cases passed, including recorded absence with a real zero rate versus missing attendance, and suppressed presence flags. Ruff, TypeScript, 117 web tests, build, contract equality and schema-reference freshness passed. All eight PostgreSQL overview cases collected successfully; they were not run locally.

## ES

KAN-187 está asignada a Elizabeth, con deadline **27/11/2026**. Implementación Yohanna; único revisor solicitado Anasfady. El stack compone las consultas académicas existentes para el panel: contrato/permisos → asistencia → entregas → competencias → pruebas de privacidad y ámbitos. No repite fórmulas ni completa la dependencia del modelo de riesgo.

La ruta anterior exige sesión y los tres permisos de agregado existentes en la cohorte. Docencia asignada, coordinación del ámbito y administración mantienen sus atribuciones; no se conceden roles a captación ni alumnado. Incluso para docencia, la respuesta siempre es agregada, sin filas individuales.

El periodo inclusivo `attendance_from`/`attendance_to` afecta solo a asistencia. Entregas usa actividades publicadas actuales y su `as_of`; competencias usa la versión actualmente asignada. `generated_at` no garantiza un snapshot histórico o transaccional de todas las consultas.

Las sumas de asistencia son días-persona; su tasa es una proporción 0–1 y queda nula sin registros. Las entregas se cuentan por actividad; `reviewed` se solapa con estados entregados y no se suma a los cuatro estados excluyentes. Competencias conserva niveles 1–3 y «sin evaluar», nunca nivel cero ni un porcentaje global inventado.

Se reutilizan consultas y cálculos existentes, excluyendo bajas voluntarias y conservando matrículas finalizadas. La supresión de grupos pequeños se aplica a todos: los conteos y la presencia de datos quedan nulos. El significado de `has_data=false` depende de cada bloque y no equivale a un resultado cero.

No se exponen nombres, correos, identificadores de alumnos/matrículas, URLs, contenido de entregas, evidencias o motivos libres de asistencia. Solo quedan identificadores/etiquetas de recursos académicos y agregados. La auditoría de consulta completada se registra una vez, tras componer todo; un fallo no confirma una consulta exitosa. No cambian modelos, migraciones, reglas de admisión, acceso académico, roles ni allowlist del asistente.

Las pruebas offline usan despacho HTTP real con dobles de principal/base y cálculos de asistencia existentes; no acreditan autenticación o ejecución PostgreSQL. Los casos PostgreSQL se recopilaron, sin ejecutarlos localmente. Riesgo ML, métrica administrativa del 70%, KPIs aceptados por cliente, UI y consultas históricas quedan fuera. No se cambia Jira ni se fusiona o despliega; no se espera al CI.

Evidencia del 25/11: 44 casos offline PASS, distinguiendo también ausencia registrada con tasa cero de falta de registro. Ruff, TypeScript, 117 pruebas web, build, igualdad de contrato y frescura del diccionario PASS. Los ocho casos PostgreSQL se recopilaron correctamente, sin ejecutarlos localmente.
